## 1. Контекст

Проект получил ревью тестового задания. Часть замечаний — прямые пробелы
(нет axios, socket.io не подключён, нет i18n, нет форм, нет 404, нет кастомных хуков),

### Что ревьюер оценил положительно (не ломать)

- Структура: страницы и компоненты раздельно, мок отдельно, стор отдельно.
- Декомпозиция страниц.

- Переиспользуемые утилиты `formatDate` и `getOrderStats`.
- Глобальный layout, оборачивающий приложение.
- Удаление через модалку подтверждения.
- `setInterval` для часов с корректной отпиской.

## 2. Принятые решения

| Вопрос         | Решение                                                                        | Обоснование                                                                                                                                                      |
| -------------- | ------------------------------------------------------------------------------ | ---------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Архитектура    | Фронт (Next) и API (NestJS) — **два отдельных репозитория**                    | API может быть передан другой команде; разделять дешевле сейчас, чем потом                                                                                       |
| Фронт          | **Одно** Next-приложение, без монорепо и Turborepo                             | Micro Frontend снят → делить нечего; оркестрация обычными npm-скриптами (пункт ТЗ «Task Runners»)                                                                |
| Бэкенд         | NestJS                                                                         | Из коробки модули, guards под JWT, `@nestjs/graphql`, `@nestjs/websockets`. Альтернатива — Express, экономит ~1 день, но всё пишется руками                      |
| Стейт-менеджер | Остаёмся на **Redux Toolkit**                                                  | Ревьюер стор уже одобрил; `listenerMiddleware` закрывает EDA, `createAsyncThunk` — состояния загрузки. Zustand не даёт выигрыша и добавляет риск новых замечаний |
| Хранилище API  | **In-memory + абстракция репозитория**, Postgres — опциональная последняя фаза | Микросервисов нет, инстанс один, БД в ТЗ не требуется. Ревьюеру не нужно поднимать Postgres. Переезд = один новый класс                                          |
| Контракт FE↔BE | GraphQL-схема + OpenAPI, типы через `graphql-codegen` / `openapi-typescript`   | Не нужен общий npm-пакет типов — главная боль поли-репо                                                                                                          |
| socket.io      | Счётчик активных сессий                                                        |                                                                                                                                                                  |
| Формы          | **Formik + Yup**                                                               |                                                                                                                                                                  |
| Стили          | Bootstrap + левый сайдбар                                                      | Без миграции на Tailwind                                                                                                                                         |
| i18n           | `next-intl`, локали **RU / EN / UK**, выбор через cookie                       |                                                                                                                                                                  |
| Тесты          | **Vitest + RTL + MSW + Playwright**                                            |                                                                                                                                                                  |
| Порядок работ  | Сначала блок 1 (фидбек), затем блок 2 (ТЗ)                                     | Предъявляемый результат к концу первой недели                                                                                                                    |

### Отклонённые варианты

- **Module Federation** для микрофронтендов — `@module-federation/nextjs-mf` официально
  не поддерживает Next 15 + Turbopack, потребовался бы откат версии Next.
  (Пункт снят из скоупа целиком.)
- **WASM на Rust** — тянет Rust-тулчейн в Docker-образ. (Пункт снят.)
- **`next-pwa`** — проект заброшен, берём Serwist.
- **RTK Query** — увёл бы axios на второй план, а ревьюер требует его явно.

## 3. Текущее состояние кода

Актуально после фазы 1.3. Что нужно держать в голове, приступая к работам:

- **SSR отсутствует.** Страницы клиентские, данные грузятся хуками

- **Хардкод локали:** `"ru-RU"` в `src/components/topMenu/index.tsx`,
  `"Все типы"` в `src/components/select/index.tsx`, тексты модалки и карточек.
- **Сокет подключён.** `src/services/socket.ts` держит соединение с
  переподключением, `src/lib/listenerMiddleware.ts` раскладывает события по
  стору, счётчик сессий лежит в слайсе `session` и показан в шапке компонентом
  `sessionCounter`. Остальное наполнение топбара — фаза 1.4.
- **`NavigationMenu` теперь внутри `StoreProvider`** (раньше стоял выше него и
  контекста Redux не видел). Любой компонент шапки может читать стор.
- **Фронт ходит в API.** `src/services/http.ts` (транспорт) → `src/services/api/*`
  (типизированные методы с разбором ответа) → thunk'и слайса → стор. Мок
  `src/mocks` отключён от приложения и ждёт решения в фазе 2.6 (`TODO(2.6)`).
- **Ошибки видно, но грубо:** алерт `alert-danger` над списком с кнопкой
  «Повторить», без автоскрытия. Причёсывается в фазе 1.4.
- **Кастомные хуки в `src/hooks/`** — загрузка данных, часы, сокет, модалки,
  localStorage. Компоненты не диспатчат `fetch*` напрямую; в `@/lib/hooks`
  остались только типизированные обёртки Redux.
- **Адрес API задаётся окружением** (`NEXT_PUBLIC_API_URL`, для серверной
  стороны — `API_URL_INTERNAL`), см. `.env.example`. Без файла берутся
  дефолты — `http://localhost:4000`.

Закрыто в фазе 1.1: JS-файлы, разъезд `id` между `string` и `number`, мок как
JS-модуль, отсутствие линтера и форматтера.
Закрыто в фазе 1.3: axios и слой запросов, загрузка через `createAsyncThunk` с

Закрыто в фазе 1.2: появился API-репозиторий — `orders`, `products`, каскадное

**Структура выровнена:** приложение больше не лежит в подпапке `my-app/` —

#### Отклонение от плана

**Порт хранилища — один обобщённый интерфейс, а не два.** В чеклисте написано
«интерфейсы репозиториев», но у заказов и продуктов контракт совпадает
дословно, поэтому в `domain/repository.ts` объявлен
`Repository<TEntity, TDraft, TId>`, а `OrdersRepository` и `ProductsRepository` —
его псевдонимы с подставленными типами. В пункте 5 они разошлись:
`ProductsRepository` дополнен методом `removeByOrder` — заказам он не нужен,
и в общий порт не попал.

**Внедрение через `Symbol`-токен, а не через абстрактный класс.** Интерфейс
существует только в типах, у Nest-провайдера должна быть runtime-ссылка.
Абстрактный класс дал бы токен без `@Inject`, но перестал бы быть чистым
контрактом — в него легко просачивается реализация. Токены объявлены рядом с
псевдонимами (`ORDERS_REPOSITORY`, `PRODUCTS_REPOSITORY`), выбор реализации
живёт в единственном месте — в `providers` модуля.

**Генерация `id` переехала из сервиса в репозиторий.** Это аналог
автоинкремента: id выдаёт хранилище, потому что только оно знает про уже
существующие записи. Сервис теперь не трогает данные вообще.

**Каскад вызывается напрямую, а не через доменное событие.** Соблазн был:
шина уже есть, `ProductsService` мог бы подписаться на `order.deleted`. Но без
удаления продуктов данные остаются битыми, а обязательный шаг нельзя отдавать
на волю подписчиков — событие рассылает уведомления, и «никто не подписался»
для него нормальная ситуация. `OrdersModule` импортирует `ProductsModule`
и зовёт метод явно; обратной зависимости нет, цикла не возникает.

**При каскаде отдельные `product:deleted` не рассылаются.** Клиент получает
`order:deleted` и убирает продукты заказа одним действием — редьюсер
`deleteAllOrderProduct` во фронтовом сторе уже так и устроен. Десяток событий
подряд на одно действие пользователя только дёргал бы интерфейс.

**Валидация тела запроса переехала с type guard'ов на `ValidationPipe`.** Guards
из `domain/types.ts` остались, но теперь только для сида: `seed.json` — тоже
внешние данные, и разбирать их надо на границе. У HTTP-DTO появились классы
(`CreateOrderDto`, `CreateProductDto`) — `ValidationPipe` работает в рантайме
и читает метаданные декораторов, а интерфейсы после компиляции исчезают.
Поле `order` в DTO объявлено обычным `number`: в брендовый `OrderId` его
превращает контроллер, конвертация живёт на границе.

**`.env` читается через `dotenv`, а не через `@nestjs/config`.** CORS для
socket.io задаётся в декораторе `@WebSocketGateway`, а декораторы вычисляются
при загрузке модуля — до того, как Nest поднимет DI, и `ConfigService` оттуда
недоступен в принципе. `import 'dotenv/config'` первой строкой `main.ts`
наполняет `process.env` раньше загрузки модулей, а `src/config.ts` отдаёт
значения с дефолтами. `@nestjs/config` был установлен и удалён.

**Общий compose — отдельный файл `docker-compose.full.yml` во фронтовом
репозитории.** Он собирает API из соседней папки `../berkun-dzencode-api`, и
если положить это в основной `docker-compose.yml`, то у ревьюера, склонировавшего
только фронт, перестанет подниматься даже фронт. Поэтому обычный
`docker compose up` остался самодостаточным, а обе части поднимаются командой
`docker compose -f docker-compose.full.yml up`.

**`tsconfig` усилен до полного `strict`.** `nest new --strict` включает только
`strictNullChecks`, `noImplicitAny` и `strictBindCallApply`. Добавлены `strict`,
`noUncheckedIndexedAccess`, `noImplicitOverride` — те же настройки, что во
фронтовом репозитории.

**Набор npm-скриптов выровнен с фронтовым:** появились `typecheck`,
`format:check` и `verify`, а `lint` разделён на проверку и `lint:fix`.

- **Скрипт `format` падал** на шаблоне `"test/**/*.ts"` после удаления

#### Отклонение от плана

Ниже — записи по мере прохождения пунктов фазы; итог подводится, когда закрыт
последний.

**Пункт 1 (`services/http.ts`).**

**Ошибки нормализуются в класс `HttpError`, а не отдаются как `AxiosError`.**
Слайсы в следующих пунктах кладут ошибку в состояние, а `AxiosError` тянет за
собой `config`, `request` и циклические ссылки — Redux на такое ругается
(non-serializable value). `HttpError` — обычный `Error` с гарантированными
`statusCode` и `message` плюс метод `toApiError()`, отдающий чистый объект под
`rejectWithValue`. `statusCode === 0` означает «ответа не было вовсе» (обрыв
сети, таймаут, отказ CORS) — это единственное состояние, при котором повтор
запроса осмыслен, и для него есть геттер `isNetworkError`.

**Разбор тела ошибки не сводится к `isApiError`.** `ValidationPipe` на бэке
отдаёт `message` массивом строк, обычный `HttpException` — одной строкой, и
существующий guard пропускает только вторую форму. Массив склеивается в строку
отдельной веткой, иначе на любой ошибке валидации формы (фаза 1.4) в
интерфейсе оказалось бы `[object Object]`.

**Базовых адресов два: `NEXT_PUBLIC_API_URL` и `API_URL_INTERNAL`.** Из
браузера API виден по проброшенному наружу порту, из серверного рантайма Next
внутри docker-сети — по имени сервиса. Это ровно тот `TODO(2.1)`, что стоит в
`docker-compose.full.yml`; функция `apiBaseUrl()` выбирает адрес по
`typeof window`, так что в фазе 2.1 останется дописать переменную в compose, а
не править код. Модуль изоморфный: ни `window`, ни `localStorage`, ни React.

**Заведён `.env.example`** — раньше во фронте его не было, а теперь адрес API
задаётся окружением. В `.gitignore` добавлено исключение `!.env.example`:
правило `.env*` прятало и его тоже.

**Пункты 2–3 (`services/api/*`).**

**Ответ сервера разбирается через `parseOrder` / `parseProduct`, а не
приводится к типу через `as`.** Соблазн был большой: `http.get<Order[]>()`
пишется в одну строку и компилятор доволен. Но дженерик axios — это обещание,
а не проверка: он ничего не знает о том, что реально пришло по сети. У нас два
репозитория без атомарных изменений контракта (риск №5 в разделе 5), то есть
разъехавшийся бэк — не гипотеза. Разбор на границе оставляет расхождение в
одном месте с внятным сообщением вместо `undefined` где-то в глубине рендера.
Заодно это ровно то правило, по которому уже разбирается `seed.json`.

**Битое тело ответа — это `HttpError` с настоящим статусом (обычно `200`), а
не с нулём.** Нуль в `HttpError` означает «ответа не было вовсе» и разрешает
повтор запроса; повторять запрос, на который сервер уверенно отвечает мусором,
бессмысленно. Различие пригодится хукам и `error.tsx` в конце фазы. Признак
таких ошибок — `error: "Invalid Response"`.

**У методов свой узкий `RequestOptions`, а не `AxiosRequestConfig`.** Через
полный конфиг вызывающий код мог бы переопределить `baseURL`, `withCredentials`
или интерсепторы, и настройки транспорта расползлись бы по компонентам.
Наружу открыты только `signal` (его даёт `createAsyncThunk`) и `headers` (в
фазе 2.1 туда уйдёт `Cookie` серверного запроса). Побочный эффект — модули
`api/*` не импортируют axios вообще, кроме типа ответа в `parse.ts`.

**Списки возвращаются как `readonly`.** Массив из сети — снимок, а не рабочая
коллекция; сортировать или фильтровать его на месте нельзя, потому что дальше
он уходит в стор. Та же причина, по которой репозитории API отдают копии.

**Барреля `services/index.ts` нет, есть только `services/api/index.ts`.**
Компоненты и thunks должны импортировать `@/services/api`, а `services/http` —
внутренняя кухня транспорта: если в фазе 2.3 чтение переедет на GraphQL,
поменяется реализация этих шести функций, а не места вызова.

**Пункты 4–5 (стор).**

**Удаление тоже переведено на API, хотя чекбокс говорит только про загрузку.**
Без этого работа осталась бы заведомо сломанной: списки грузятся с сервера, а
модалка удаляет запись лишь в сторе — после перезагрузки страницы «удалённый»
приход возвращается. Добавлены thunk'и `removeOrder` / `removeProduct`: сперва
`DELETE` и `204`, и только потом изменение стора. Показывать удаление, которое
сервер отверг, хуже, чем показать ошибку.

**Каскад по продуктам переехал из `ModalWindow` в редьюсер.** Правило «`deleteOrder`
и `deleteAllOrderProduct` диспатчатся только парой» держалось на памяти
разработчика и было записано в `CLAUDE.md`. Теперь обе ветки вызываются внутри
`removeOrder.fulfilled`, а компонент диспатчит один thunk — забыть половину
каскада стало невозможно. Сами редьюсеры остались: к ним в пункте про
`listenerMiddleware` подключится слушатель socket-событий.

**Статусы и ошибки — по одному на список, а не один общий на слайс.** Приходы и
продукты грузятся двумя независимыми запросами; общий флаг означал бы, что
упавший запрос продуктов гасит уже показанные приходы. Ошибка удаления пишется
в то же поле, но статус не трогает — список остаётся валидным, сломалась
конкретная операция, и интерфейс показывает алерт **над** данными, а не вместо
них.

**Повторные запросы отсекает `condition` самого thunk'а, а не проверка в
компоненте.** Прежнее «диспатчить, только если массив пуст» не различало «ещё
не грузили» и «загрузили, сервер вернул пусто», а в дев-режиме React StrictMode
монтирует эффект дважды и слал два запроса. Теперь `condition` пропускает
запрос только из состояний `idle` и `failed` — значит повтор после ошибки
по-прежнему возможен, а гидрация из `preloadedState` (фаза 2.1, статус придёт
`succeeded`) второго запроса не вызовет.

**`RootState` выводится из отдельного `rootReducer`, а не из `makeStore`.**
Иначе `makeStore(preloadedState: Partial<RootState>)` ссылался бы на тип,
который сам же порождает, и TypeScript упёрся бы в циклический вывод. Ради
этого в `store.ts` появился `combineReducers`.

**Заведён `createAppAsyncThunk`** (`src/lib/createAppAsyncThunk.ts`) — та же
идея, что у `useAppDispatch`: типы `state`, `dispatch` и `rejectValue` заданы
один раз. Без `rejectValue: ApiError` payload в ветке `rejected` имел бы тип
`unknown` и приводился бы вручную в каждом редьюсере.

**Ошибка приводится к `ApiError` функцией `toApiError` из `services/api`.**
Слайсу нельзя импортировать `services/http` — иначе транспорт протекает в стор;
`toApiError` отдаёт готовый сериализуемый объект, а `Error` в Redux класть
нельзя.

**Пункты 6–7 (сокет и EDA).**

**Появился третий слайс — `session`.** Счётчик активных сессий не относится ни
к доменным данным (его нельзя запросить и он ничей не атрибут), ни к выбору
пользователя, а оба существующих слайса имеют жёстко очерченный смысл. Там же
живёт `isSocketConnected`: при разрыве счётчик сбрасывается в ноль, потому что
пока соединения нет, сессии приходят и уходят без нашего ведома, и показывать
последнее известное число — врать.

**Подключением командуют экшены `socketConnectionStarted` /
`socketConnectionStopped`, а не вызов функции из компонента.** Подписка живёт
вне React, её видно в devtools, и запустить её можно откуда угодно. Сам
слушатель — долгоживущий эффект RTK: после подписки он ждёт `await
listenerApi.condition(socketConnectionStopped.match)` и на выходе отписывается.
`cancelActiveListeners()` в начале гарантирует ровно одну подписку, что важно в
StrictMode с двойным монтированием.

**События проходят разбор на границе, как и HTTP-ответы.** Типизированный
`Socket` обещает форму payload'а, но по проводу приходит произвольный JSON.
`parseServerEvent` проверяет поля и превращает числа в брендовые `OrderId` /
`ProductId`; битое событие пишется в `console.warn` и до стора не доходит.

**Список типов событий продублирован в `services/socket.ts`, а не добавлен в
контракт.** Подписаться можно только по рантайм-списку, а `ServerEvent`
существует лишь в типах. Класть массив в `types/socket.ts` не стал: этот файл —
зеркало `domain/events.ts` бэкенда, и односторонняя правка развела бы копии.
Вместо этого `as const satisfies readonly ServerEventType[]` плюс проверка
`Exclude<…> extends never`: новое событие в union'е ломает компиляцию, если про
него забыли подписаться.

**`order:deleted` разворачивается в тот же каскад, что и `removeOrder`.** Сервер
при удалении прихода не рассылает отдельные `product:deleted` (решение фазы
1.2), поэтому слушатель диспатчит `deleteOrder` и `deleteAllOrderProduct`
парой. Собственное удаление приходит обратно эхом и применяется повторно —
редьюсеры идемпотентны, фильтр по уже удалённому id ничего не меняет.

**Счётчик сессий показан в шапке досрочно** (пункт из фазы 1.4), потому что без
него сокет — работающий, но невидимый код: проверить его можно было только
запуском скрипта. Компонент `sessionCounter` рядом с часами показывает точку
состояния связи и число вкладок, а при разрыве — «нет связи» вместо
устаревшего числа. Заодно выяснилось, что `NavigationMenu` рендерился **выше**
`StoreProvider` и стор ему был недоступен; шапка перенесена внутрь провайдера.

**Старт и стоп подписки висят на `StoreProvider`** — теперь через хук
`useSocket` в крошечном компоненте `SocketConnection` внутри провайдера
(`useAppDispatch` требует, чтобы `<Provider>` уже стоял выше).

**Пункты 8–11 (хуки и служебные роуты).**

**У каждого хука есть вызывающий код — иначе это не хук, а заготовка.**
`useOrders` / `useProducts` заменили `useEffect` с диспатчем на обеих
страницах, `useClock` — таймер в `topMenu`, `useSessionCount` — селекторы в
`sessionCounter`, `useSocket` — эффект в `StoreProvider`, `useConfirm` — три
одинаковые тройки `useState` в карточках, `useOrderStats` — расчёт статистики,
`useLocalStorage` — фильтр по типу на странице продуктов. Написать восемь
файлов и оставить их лежать было бы честнее не делать вовсе.

**`OrderCard` считает статистику сам.** Раньше её вычисляла страница и
передавала шестью пропсами (`productsCount`, `priceUSD`, `priceUAH`, `date`,
`dateShort`, `title`); теперь карточка принимает `order` целиком, а суммы берёт
из `useOrderStats`. Прежний список пропсов был следствием того, что считать
было негде, — с появлением хука необходимость отпала.

**Список приходов вынесен в компонент `ordersView`.** Страниц стало две —
`/orders` и `/orders/[id]`, — и вторая показывает ровно то же самое. Дублировать
разметку ради выбранного из адреса прихода незачем.

**`/orders/[id]` — серверный компонент, а внутри клиентский `OrderDeepLink`.**
Разделение не косметическое: проверить формат номера можно до отправки ответа
(и вернуть настоящий HTTP 404), а проверить существование прихода — только
после загрузки списка, то есть уже на клиенте. Отдельного `GET /orders/:id` на
бэке нет, и заводить его ради одного экрана не стал.

**`SelectCustom` стал управляемым.** У него было собственное состояние
выбранного типа, и восстановленный из localStorage фильтр применялся бы к
списку, а сам `<select>` показывал «Все типы». Значение теперь приходит
пропом — один источник правды.

**`useClock` до первого тика отдаёт `null`.** Время на сервере и в браузере
различается по определению, поэтому первый рендер обеих сторон обязан быть
одинаковым; часы появляются сразу после монтирования, место под них
зарезервировано неразрывным пробелом, чтобы шапка не подпрыгивала. Это заранее
снимает риск №1 из раздела 5.

**Появился флаг `force` у thunk'ов загрузки** — и заодно закрыл пункт,
отложенный при работе с сокетом: после переподключения слушатель перезагружает
оба списка, потому что пока связи не было, события удаления шли мимо.
Тот же флаг стоит за кнопкой «Повторить» в алерте ошибки.

**Пункты 4–5.** На первом рендере статус равен `idle`, и условие «показывать

`types/api.ts` — заодно им будут пользоваться хуки `useOrders` / `useProducts`
в следующем пункте.

**Пункты 4–5.** Ушло предупреждение `react-hooks/exhaustive-deps` в
`orders/page.tsx`, которое висело с фазы 1.1: эффект больше не читает `orders`

`npm run verify` и `npm run build` зелёные. Предупреждение `exhaustive-deps`,

Пункт 1 проверялся **в рантайме против запущенного API** (`:4000`), а не только
компилятором: `GET /orders` → 200 и 7 записей, `GET /products` → 34 записи;
`baseURL` `http://localhost:4000`, `withCredentials: true`, таймаут 10 с.
Нормализация ошибок — 404 → `{ statusCode: 404, message: "Cannot GET …",
error: "Not Found" }`; 400 от `ValidationPipe` → пять сообщений валидации,
склеенных в одну строку; недоступный порт → `statusCode: 0`,

`error: "ECONNABORTED"`; произвольный `Error` через `HttpError.from` →
`statusCode: 0`. Отдельно проверено, что `baseURL`, заданный на конкретном

интерсептора.

Пункты 2–3 проверялись так же, против живого API, полным циклом:
`getOrders()` → 7 разобранных приходов, `getProducts()` → 34 продукта;
`createOrder()` → приход с выданным сервером `id: 8`; `createProduct()` на этот
приход → продуктов стало 35; `deleteOrder(8)` → приходов снова 7, продуктов 34,
сирот с `order: 8` — ноль (каскад бэка отрабатывает через этот слой);
`createProduct()` + `deleteProduct()` → счётчик вернулся к 34, записи нет.
Ошибки: удаление несуществующего прихода → `HttpError 404 "Заказ 999999 не
найден"`, `createOrder` с пустыми полями → `HttpError 400` со склеенными
сообщениями `ValidationPipe`.

Разбор ответа проверялся отдельно на подставных телах: массив валидных заказов
проходит; объект вместо массива → `HttpError` со `statusCode: 200`,
`error: "Invalid Response"`, сообщением «Ожидался массив, пришло: object»;
битая запись внутри массива и битая сущность → то же самое с текстом от
`parseOrder`. `apiBaseUrl()` в серверном рантайме отдаёт `API_URL_INTERNAL`,
а без него откатывается на публичный адрес.

Изоморфность пункта 3 проверена не рассуждением, а рендером: во временную
страницу `app/smoke-check/page.tsx` (серверный компонент, `force-dynamic`)
добавлен вызов `getOrders()` и `getProducts()`, дев-сервер отдал готовый HTML
с `renderedOn: "server"`, `orders: 7`, `products: 34` — то есть запрос ушёл из
серверного процесса Next, а не из браузера. Страница после проверки удалена.

Пункты 4–5 проверялись прогоном настоящего стора в Node против живого API:

- пустой стор → `idle`/`idle`; во время запроса оба статуса `loading`, списки
  пусты; после — `succeeded`, 7 приходов и 34 продукта;
- повторный `dispatch(fetchOrders())` возвращает `rejected` с
  `meta.condition === true` и состояние не меняет (StrictMode больше не шлёт
  второй запрос);
- `removeOrder` на специально созданном приходе с одним продуктом: в сторе
  исчезли и приход, и его продукт (сирот — ноль), на сервере тоже;
- `removeOrder(999999)` → `ordersError = { statusCode: 404, message: "Заказ
999999 не найден" }`, при этом `ordersStatus` остался `succeeded`, а список
  из 7 приходов на месте;
- при недоступном API (`:4999`) оба статуса `failed`, в обеих ошибках
  `statusCode: 0` и `ECONNREFUSED`, повторный запрос `condition` уже не
  блокирует — retry после сбоя возможен;
- `makeStore({ ordersAndProductsData: … })` поднимает стор с готовыми данными,
  UI-слайс при этом получает свой `initialState`, а `fetchOrders()` на таком
  сторе отменяется по `condition` — то есть гидрация из SSR не приведёт к
  повторной загрузке.

Отрисовка проверена на дев-сервере: `/orders` и `/products` отдают `200`, в
серверной разметке по восемь скелетонов (первый рендер со статусом `idle`),
ошибок в логе Next нет.

**Чего проверка не покрывает:** клиентский цикл «эффект → запрос → список» в
настоящем браузере не гонялся — headless-браузера в проекте нет, Playwright
появится в фазе 2.6. Логика стора проверена напрямую, но клик по «Удалить» в
живом интерфейсе стоит посмотреть глазами. Дев-сервер при этом должен слушать
`:3000`: `CORS_ORIGIN` бэкенда по умолчанию разрешает именно его.

Пункты 6–7 проверялись тем же способом — настоящий стор в Node против живого
API (в Node подставлен `globalThis.window`, иначе `getSocket()` намеренно
отдаёт `null`):

- `socketConnectionStarted` → `isSocketConnected: true`, счётчик сессий пришёл
  сам;
- подключение второго клиента поднимает счётчик на единицу, отключение —
  опускает;
- удаление прихода **другим клиентом** (прямой `DELETE` мимо этого стора)
  убирает из стора и приход, и его продукт — каскад по `order:deleted`
  отрабатывает; удаление продукта убирает продукт;
- принудительный обрыв транспорта (`socket.io.engine.close()`) даёт
  `isSocketConnected: false` и обнуление счётчика, после чего клиент
  переподключается сам и счётчик восстанавливается;
- `socketConnectionStopped` → отписка: следующее удаление на сервере до стора
  уже не доходит.

**Проверка в настоящем браузере всё-таки состоялась, хоть и случайно.** Разбор
«лишней» сессии в счётчике показал, что соединение с API держит процесс Chrome:
на `:3000` работает дев-сервер, вкладка с приложением подхватила новый код и
подключилась к сокету сама. То есть клиент собирается и работает не только в
Node.

Пункты 8–11 проверялись на дев-сервере запросами по всем маршрутам:

- `/no-such-page` → HTTP 404 и разметка `not-found.tsx`;
- `/orders`, `/orders/1`, `/products` → HTTP 200 с заголовком страницы и
  восемью скелетонами;
- `/orders/abc`, `/orders/-5`, `/orders/99999999999999999999` → сегмент уходит
  в `notFound()` (без `loading.tsx` — честный HTTP 404, см. отложенное выше);
- в логе Next после финальной сборки ошибок нет.

Флаг `force` проверен против живого API на настоящем сторе: первый
`fetchOrders()` грузит, второй отсекается `condition`, `fetchOrders({ force: true })`
проходит и подхватывает приход, созданный мимо стора, а после удаления —
возвращает список к прежнему размеру.

**Чего проверка по-прежнему не покрывает:** клиентские переходы в браузере
(клик по карточке, показ 404 после загрузки списка, восстановление фильтра из
localStorage) — headless-браузера в проекте нет до фазы 2.6. Серверная часть
каждого из этих маршрутов проверена, клиентская — логикой стора и хуков.

## 5. Риски и подводные камни

1. **Гидрация дат (фаза 2.1).** `formatDate` и часы на сервере и клиенте дадут разный
   результат из-за таймзоны → hydration mismatch. Форматирование фиксируем на UTC,
   часы рендерим только на клиенте.
2. **Переделка из-за порядка работ.** Feedback-first означает, что клиентская загрузка
   из 1.3 переводится на SSR в 2.1. Чтобы это стоило часы, а не день: вызовы api сразу
   пишем изоморфными, `StoreProvider` с первого дня готовим под `preloadedState`.
3. **socket.io требует long-running сервер** — деплой на Vercel отпадает, нужен Docker/VPS.
4. **In-memory ломается при масштабировании.** Пока инстанс API один — всё корректно.
   Два и более — у каждого свой массив, счётчик сессий разъезжается. Лечение:
   фаза 2.8 + Redis-адаптер для socket.io. Для текущего скоупа не требуется.
5. **Два репозитория — нет атомарных изменений контракта.** Меняя API, сначала
   выкатываем бэк, потом перегенерируем типы на фронте. Локальная разработка требует
   поднять оба — закрывается общим compose.
6. **Cookie между разными портами в dev.** `SameSite=Lax` + разные origin фронта и API
   потребуют аккуратной настройки CORS `credentials` и, вероятно, прокси через Next
   rewrites на время разработки.
